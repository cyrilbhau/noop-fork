# Cross-stage rulings addendum

Written 11 November 2026 by the orchestrator, after two reconciliation passes over the seven
specifications and an independent re-check. These rulings are binding on every stage and override
any specification text that still disagrees with them. A test author or implementer who finds such
text follows the ruling and says so in the hand-off note.

| # | Ruling |
|---|---|
| A1 | **Settings and Health order.** Top to bottom: Scorecard, Coach packet, Intake, Body record, Events, Niggle log, Recovery context, Timeline. Each **Health row** is present only while its own flag is on. Each **Settings card is always drawn on iPhone**, because it holds that flag's switch. |
| A2 | **Stage 4 internal order.** 4-4a (catalogue), then 4-7 (laboratory units), then stage 1's work package 1-11 (the weigh-in-outranks-scan rule), then 4-4c, 4-5, 4-6 and the hotspot package. Work package 4-7 **creates** `Strand/Data/BodyRecordPresenter.swift` with the editor draft type and 4-5 extends it. In `Strand/Screens/LabBookView.swift` the order is 4-7's "Entered as" line first, then 4-6's CSV scope argument. |
| A3 | **The weigh-in-outranks-scan rule** lives in stage 1 §8.7 (ruling R44): `BodyMeasurementResolver.withoutOutrankedScans(_:asOf:)`, with `BodyMeasurementResolver.weighInSource`. No other specification restates it. It is implemented in stage 4's step, after 4-4a and before any stage 4 edit of the files it touches. |
| A4 | **Debug demo registry.** One registry element per stage, and an element may own several prefixes. Reserved: scorecard's existing unprefixed names; `packet-`; `intake-`; `bodyrecord-`, `scan-`, `compare-`, `bench-`, `labunits-`; `events-`; `niggle-`, `cutstress-`, `timeline-`; `labbook-`. No two elements may claim overlapping prefixes. |
| A5 | **Packet version 2 budget.** `8000 + 290 × rangeDays + PersonalEvents.packetByteAllowance` bytes, as stage 2 §7.12 gives it. Packet v2 is described in stage 2 §7.12 and §14.1. |
| A6 | **One order for every shared file:** Lab Book ownership, stage 2, stage 3, stage 4, stage 5, stage 6, then packet v2. The string catalogue has one writer at a time, and it runs last in each step. |
| A7 | **One Fixture Person** across all stages: stage 1 §13 is the reference for identity, dates, weights and waists. |
| A8 | **No Android work** (stage 1 ruling R43). Where a stage changes a contract shared with Android, the specification states the drift and nothing is written in Kotlin. |
| A9 | **`CanonicalDay.number(_:)` and `CanonicalDay.key(_:)`** exist once, in `Packages/StrandAnalytics/Sources/StrandAnalytics/CanonicalDay+Surface.swift` on the integration branch, as forwarders to `dayNumber(_:)` and `key(dayNumber:)`. No stage declares them again. |
| A10 | **Lab Book ownership: two different readings at one instant are two readings.** Review finding, confirmed by replay against the store. When rows under different strap ids share marker, instant and source but differ in content, they are *conflicting* readings and both are kept and listed (the owner's decision). Therefore: an edit changes **only the row the owner edited**, selected by its row id, plus its *true copies* (rows equal to it in every column except id and device id); it never changes a conflicting row. A delete removes only that row and its true copies. A save that lands on an existing instant updates the row it lands on and that row's true copies. This overrides labbook-ownership.md §7.4 wherever it says an owner-scope write applies to every row at the identity. |
| A11 | **Lab Book ownership: the projection is never a reason to lose information.** The one-time repair and every write re-derive only the projected cell of the reading being written. The repair never replaces a projected value that equals the value of any stored reading for that marker and day, and never erases a cell that no stored row backs (it may be the last trace of an earlier reading). Where conflicting readings fall on one day, the projection keeps the value already there; if none is there, it takes the reading the listing shows first. Where true copies carry different stored days, both days keep their cell. Showing a day twice in a derived chart is accepted; losing a value is not. |
| A12 | **Lab Book ownership and the in-app Coach.** After the change the Coach context may include Lab Book readings stored under earlier strap ids that it did not see before. That is the intended effect of "nothing is hidden", and the specification states it. |
| A13 | **Lab Book ownership: an explicit write supersedes a trace.** A11's "never erase a cell no stored row backs" binds the repair and every write to *another* reading. When the owner adds a reading for a marker and day whose cell is unbacked, the new reading takes the cell, and deleting that reading removes the cell. Real data the owner entered outranks the trace of an older one. |
| A14 | **Lab Book ownership: a value stays projected while any stored reading holds it.** When a reading is deleted or edited, its number is treated as having left the projected cell only if no remaining reading of that marker and day still holds that number. Deleting an unrelated reading that happens to share the number never flips a conflict day's cell. |
| A15 | **Lab Book ownership: no index migration in this change.** The owner-scope reads scan `labMarker` by marker, instant and source without a device-free index. For the size of a personal Lab Book this is accepted. Two device-free indexes would remove the scan; they are a database migration and wait for the owner's go-ahead as a separate change. |
| A16 | **Stage 4 overflow and sign.** A sum of sides that overflows is `notAvailable(.invalidComponent)` with no source. A delta that overflows saturates at ±`greatestFiniteMagnitude`. A percent that overflows is nil. `parseEntry` never returns negative zero. `toStored` and `fromStored` match an option label exactly; only `storedValue` folds labels. No output is ever infinite or NaN. |
| A17 | **Stage 2 packet details.** Free text is trimmed again after the 48-byte cut, so it never ends in a space. The privacy scan treats six hexadecimal pairs separated by colons or dashes **in any mixture** as a hardware address and fails closed. For an invalid range the header reads `sections: none` and the switched-off line reports the owner's switches as usual. When two body readings of one kind fall on one day the later in the input wins, as for days and steps. A body reading whose day is not a canonical key is ignored and never printed. |
