# WHOOP 4.0 collection and analytics audit

Baseline: upstream `ryanbr/noop` commit `8e4b0c16e7640607600fa6bde5424095eba6034e`, inspected on 21 October 2026. This is a source audit; no iPhone, band, firmware, overnight run, or physical accuracy result was available. Existing test files show intended coverage, not a claim that those tests ran. See the separate validation report for executed commands.

## Decision affecting the project

**The requested reliable, phone-free step counter is not established by this engine.** NOOP's WHOOP 4.0 path estimates steps from sparse gravity-vector movement, calibrated against phone-counted days. It does not decode individual footfalls or a strap-reported step total. A display redesign cannot resolve that limitation. The current daily orchestration emits an estimate only when that day has no positive Apple Health step reference (`IntelligenceEngine.swift:2704–2712`, `:2803–2807`). Carrying the phone for part of the day can therefore suppress an estimate even when a later phone-free walk is missing from the measured phone total; this is not gap-aware step fusion.

The smallest practical alternative is measured iPhone steps through Apple Health, labelled with their source. That requires carrying the phone. A separate device that records steps to Apple Health can cover phone-free walks, but owning such a device has not been assumed. A 4.0 motion-derived estimate remains an optional, explicitly estimated readout until independent walk and sedentary tests establish useful accuracy. No purchase or subscription is required by this audit.

## Firmware and layout caveats

Firmware version and historical-record layout are different identifiers. Capture both locally during the owner's first connection; no installed firmware has been identified in this task, and no firmware update is proposed.

- WHOOP 4.0 v25 records supply timestamp and gravity but deliberately emit empty R-R, with no stored per-second HR (`WhoopProtocol/PostHooks.swift:345–374`). A sync containing only those records cannot by itself supply all overnight metrics.
- Unmapped 4.0 layouts attempt the v24 field map only if gravity magnitude and HR pass plausibility checks; otherwise those biometrics are discarded (`PostHooks.swift:377–438`). A plausibility check is protection against nonsense, not proof of a complete map.
- `HistoricalLayoutSupport.swift:39–50` distinguishes unmapped 4.0 records from supported signal-bearing records; WHOOP 5/MG raw-only layouts are a different case and do not establish 4.0 support.
- Temperature and raw SpO₂ are present only in full DSP sleep records on 4.0. A healthy-looking HR/R-R-only offload can still have zero temperature rows (`Backfiller.swift:132–135`).
- Stale RTC correction requires a valid clock reference. The offload records whether an identity reference was used and where timestamps landed (`Backfiller.swift:139–153`). An old date or future-record rejection can explain apparently missing sleep even when bytes arrive.

## Diagnose each layer separately

Use only aggregate counts, timestamps, local reason codes and app/firmware/layout versions in shared diagnostics. Existing optional Test Centre traces can include raw health values, timestamps, identifiers and full frames: inspect/redact locally before sharing, and never commit an export, database, personal log or credential.

| Layer | Evidence to collect locally | What it does and does not prove |
| --- | --- | --- |
| Radio / collection | Connection and bond state; valid/CRC-rejected frame counts; sync start/end and reconnect times. | Frames arriving proves radio traffic, not meaningful sensor content. |
| Decode / persistence | `Backfill: session persisted N rows (M with motion, T skin-temp) across K night(s)`; separate HR/R-R/motion counts and earliest/latest stored timestamps; layout-support and clock/persistence error codes. | `Backfiller.swift:407–409` generates the summary. Motion/temp zeros identify missing inputs that HR alone hides. A stalled persist must hold trim/ack. |
| Calculation | Sleep detection/skipped-window reason; valid R-R window counts; calibration day count; whether `steps_est` exists; whether a result is HR-only; baseline readiness. | An input gap is different from a calculated nil; inspect source and window before changing algorithms. |
| Display / export | Displayed source, observed timestamp, estimate label and data freshness; compare the same stored window to HealthKit records and widget snapshots. | A rendered number or open Bluetooth link does not prove a fresh measurement or successful HealthKit write. |

Existing isolated test suites worth running include `StepsEstimateEngineTests`, `StepsCounterTests`, `StepsDailyTests`, `SleepStagerTests`, `SleepStagerV2Tests`, `SleepStagerHrOnlySessionsTests`, `HrvOverCountGateTests`, `AnalyticsEngineRefusedMainNightHrvTests`, `HRVAnalyzerTests`, `SkinTempAnalyticsTests`, and protocol historical/layout tests. App-hosted backfill and Today wiring tests live in `StrandTests` and require Xcode on macOS; package success does not compile or validate that app path.

## Review priorities before a custom interface

1. Complete the unchanged iOS build and first device connection. Record actual firmware/layout and counts across each stream.
2. Isolate the 4.0 motion estimate in the phone-free walk and sedentary tests. A phone-sourced Today count must not produce a false pass. Set practical tolerances with the owner before evaluation; if unmet, keep estimated steps visibly secondary and offer a measured source.
3. Validate several locked-phone nights and one full workout, then returning in range for complete backfill. Inspect both sleep boundaries and R-R/motion coverage, not only dashboard scores.
4. Preserve the distinction among measured HR/R-R/raw ADC, locally calculated metrics, and historical vendor imports. Temperature and SpO₂ need especially explicit labels.
5. Preserve decoded data plus a verified recoverable backup. Raw recording can help re-decoding but should have bounded, documented retention and private storage, rather than unrestricted health-bearing debug logs.

No protocol, analytic formula, BLE lifecycle, firmware, HealthKit record, or device was modified for this audit.
